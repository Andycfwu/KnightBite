## Which SHA is checked

The single workflow job is **`KnightBite release verification`**, supplied by GitHub Actions (app ID **15368**). It runs without path filters on pull requests, pushes to `main`, and pushes matching `codex/release-*`. It records the checked commit/tree and asserts checkout HEAD equals `GITHUB_SHA`; no deployment commands or hosting credentials are used.

- Release-branch **push** checks the exact candidate commit **C**.
- A **pull_request** run normally checks GitHub's prospective merge commit **T**, which differs from C. Keep this integration check as well as the candidate check.
- Squashing/merging creates final main commit **M**, which cannot be named truthfully before GitHub creates it. The **main push** run must independently finish with `conclusion: success` on **M**. The Vercel deployment's Git SHA must also be **M**. A green check on C or T alone never authorizes M's promotion.

GitHub can evaluate the test-merge check for a PR when it exists. Never manually attach a successful status to M based on an older run, use a check with a different producer, or treat skipped/neutral as release approval. [GitHub workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [required status checks](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
